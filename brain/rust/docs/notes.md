The split is right. Gate the deliberate bulk runs, and leave the per-session path alone. A few of the premises are off, and those decide how it should be built.

**What holds.** `fact_curator.py` is a library. `backfill_facts.py` calls it two ways: `--file` from `session_end.py`, and the four bulk modes (`--all`, `--from-db`, `--from-perplexity`, `--from-cursor-db`). One `batch_id` covers a whole invocation, and `rollback_batch` already finds that batch through `curation_events` where the decision is `ADD`, `UPDATE`, or `MERGE`. Putting the before/after check inside the curator would tax the small path. Putting it on the bulk entry points is the right layer. That is a narrower reading of G5 than the spec, and it is the correct one.

**The gate is not a working automatic procedure today.** `start_backfill_batch` and `finish_backfill_batch` exist in `store.rs` and are only called from Rust tests. The Python backfill never inserts a `backfill_batches` row, so nothing records `p1_before`. The rollback only runs when both `--rollback-batch` and `--rollback-baseline` are passed. The docstring in `backfill_facts.py` tells the operator to run `--rollback-batch` alone, which measures and then keeps the batch. The spec’s “already gated” description is ahead of the code.

**The session path is also smaller than the note says.** `session_end.py` launches `--file` only when `BRAIN_FACT_EXTRACT=1`, and it launches it in the background. `~/.claude/settings.json` has no Stop hook, so that path is not firing on every session end right now. Leaving it ungated is still right if it gets turned back on: a full retrieval pass after a handful of facts is the wrong cost. The residual risk is real and should stay named. Each `--file` run gets its own batch id, and an `UPDATE` or `MERGE` can hide one existing fact that a gold query depends on. Many ungated sessions can add up to a regression with nothing single to roll back. That wants a later periodic check, not a hook gate.

**Do not use the default k-fold as the oracle.** `retrieval_eval_kfold.py` scores each memory as a query against its own body. That self-match is the eval the 27 October pass already threw out. The rollback example in that file only becomes a real gate with `--facts-only` and a gold file. The before and after numbers have to come from the same gold set you already trust (`gold_mined` / `retrieval_eval.py`). Capture `p1_before` once, at the start of a fresh bulk run, and store it. A retry with `--batch-id` must reuse that stored baseline. Remeasuring on resume scores a corpus the batch has already changed.

Skip the gate on `--dry-run` and on a small `--limit`. A canary should not pay for a full gold pass. There is a second copy of both scripts at `brain/backfill_facts.py` and `brain/retrieval_eval_kfold.py`. The tools copies are the ones to change.

Rollback itself is the right undo: delete the new facts and clear `superseded_by` on the rows they hid. That restores the previous history. The eval reads SQLite directly, so after a rollback the running `brain_api` index can still serve the deleted facts until it restarts. The gate should say that, or the rollback looks successful while search still returns the bad rows.
