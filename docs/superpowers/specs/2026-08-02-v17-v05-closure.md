## V-17 — single shared rate-limit bucket starved the hooks

### Problem
`client_key()` (`brain_api.rs`) returned `"local"` for any request lacking an `x-forwarded-for` header, so hooks, MCP, evals, backfills and ad-hoc scripts shared **one** 120 req/60 s budget. A read-heavy client (an eval sweep, MCP searches) exhausted the bucket and hook `/save` writes then fail-soft into the spool — silent, and easy to miss. Directly threatens Success Criterion 1.

### Reproduced (live, pre-fix)
Flooding read-only `GET /stats` past 120 requests (112×200 → 429) starved the very next `POST /save` → **429, no write**. The rejected save never reached the handler, so nothing was written.

### Fix (owner chose the read/write split)
The limiter key changed from `client_key` to `(client_key, RateClass)`:

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, Debug)]
enum RateClass { Read, Write }
```

`authorize_and_rate_limit(state, headers, class)` takes the class; the limiter map is `HashMap<(String, RateClass), ClientWindow>`. Reads and writes hold **independent** 120/60 s budgets per client, so a read flood can no longer starve hook writes. No client changes required.

All 18 call sites tagged — **11 read / 7 write**; `/health` remains unlimited:

| Class | Endpoints |
|---|---|
| **Read** | `/stats` `/search` `/v1/search` `/v1/search_index` `/v1/get_observations` `/v1/timeline` `/v1/stream` `/get-episode` `/entities` `/neighbors` `/linked` `/list` |
| **Write** | `/save` `/save-batch` `/link-entities` `/feedback` `/delete` `/reflect` `PATCH /memories/:id` |

### Teeth
New bin test `read_flood_does_not_starve_writes` exhausts the read bucket, then asserts a same-client `/save` returns 200. Reverting only `save`'s class to `RateClass::Read` made it fail (`429 != 200`); restored → passes.

### Deployed + verified live
Rebuilt, `launchctl kickstart -k com.brain.api` (pid 88127 → 50800, healthy). Read bucket exhausted (`/stats` → 429) while a same-client `/save` returned **200** (id `27fd5c0c…`) — the exact sequence that returned 429 pre-fix.

## V-05 — orphan edges accumulating (two sources)

### Problem
`edges` has no FK / `ON DELETE CASCADE` to `memories`. Orphan edges (edge whose `src_memory_id` no longer exists) were accumulating and worsening on their own.

### The count was undercounted
Reads via `sqlite3 'file:...?mode=ro'` see a pre-checkpoint snapshot and miss uncommitted WAL frames. The 329 / 744 / 821 readings during verification were **low**. A WAL-aware `.backup` and a post-restart checkpoint both showed the real figure: **1190**.

> **Auditing lesson:** when counting rows in a live WAL database from an external connection, use `.backup` or force `PRAGMA wal_checkpoint` first — a `?mode=ro` read can silently undercount.

### Two distinct orphan sources — both reproduced live, both fixed

**1. Delete path never cleaned edges** (the documented ~137/day mechanism)
`store.delete_memories` deleted from `memories` / `memories_fts` only. Both live churn paths route through it — `/delete` and `/reflect` → `run_reflection` (`brain.rs:693`) — so every consolidation orphaned the deleted memory's edges.

```rust
// inside the delete loop, after DELETE FROM memories:
self.conn.execute("DELETE FROM edges WHERE src_memory_id = ?1", params![id])?;
```

**2. `link_memory_entities` inserted edges without checking the memory exists**
`/link-entities` on a never-saved id returned `{"linked":2}` and created 2 orphan edges. In production this is a race — a backfill, or a caller whose id `reflect` deleted between read and link. Memory `d292e442` orphaned with 8 edges on the *already-fixed* binary, which is what surfaced this second source.

```rust
// guard at the top of link_memory_entities:
let exists: bool = self.conn.query_row(
    "SELECT EXISTS(SELECT 1 FROM memories WHERE id = ?1)", [memory_id], |r| r.get(0))?;
if !exists { return Ok(0); }
```

TOCTOU-safe: every API operation serialises on one `brain` `Mutex`, so no delete can interleave between the check and the inserts.

### Why not `ON DELETE CASCADE`
Chose the edge-cleanup step + existence guard per "smallest change": no schema migration, no per-connection `foreign_keys=ON` discipline. A CASCADE FK would have covered both sources but is a recreate-table migration on a 44k-edge production table, and would turn the racy `/link-entities` insert into an error rather than a no-op.

### Teeth
- `delete_memories_cleans_edges` — links entities to a memory, deletes it, asserts `entities_for_memory` (which joins on `src_memory_id`) is now empty.
- `link_memory_entities_skips_nonexistent_memory` — links to a never-saved id, asserts 0 linked and 0 edges.

Each proven by reverting only its fix and watching that specific test fail, then restored.

### Deployed + verified live
Backup taken first: `~/brain-backups/v05-orphan-sweep-20260801-151704.db` (integrity `ok`, full-WAL snapshot). Rebuilt, restarted twice (delete-path fix, then link-guard). Verified:
- **delete path** — saved a fact with 3 entities → 3 edges; `/delete` → **0 edges**.
- **link guard** — `/link-entities` on a ghost id → `{"linked":0}`, **0 edges**.
- **one-off sweep** — `DELETE FROM edges WHERE NOT EXISTS (live source memory)`, canary-verified to hit 0 live edges, cleared **1190 → 0**; residual orphans from the pre-guard window swept to **0**. Orphan count held at 0 afterward.

- **`curl` header gotcha wasted time here.** `-H "content-type:application/json"` (no space after the colon) caused every `POST /save` to 400 with an empty body while GETs worked; `-H "Content-Type: application/json"` (with a space) works. If a POST 400s with no body, check the header form before suspecting the server.
